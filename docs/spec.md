# เป้าหมาย
Todo web API + หน้าเว็บ สำหรับเจ้าของคนเดียว ไม่มี login รันบน VPS ด้วย Docker

# ทำไม
จัดการงานส่วนตัว (มีวันกำหนดส่ง, ลำดับความสำคัญ, หมวดหมู่) และเปิดได้จากทุกที่ (tech-lead อนุมาน ผู้ใช้แก้ได้)

# ฟีเจอร์
- F1: todo พื้นฐาน — เพิ่ม, ดูรายการทั้งหมด, ติ๊กเสร็จ / ยกเลิกติ๊ก, แก้ชื่อ, ลบ ทั้งผ่าน API และหน้าเว็บ (ผู้ใช้)
- F2: วันกำหนดส่ง และลำดับความสำคัญของ todo (ผู้ใช้) · วันที่อย่างเดียว ไม่บังคับ · 3 ระดับ low / medium / high ค่าเริ่มต้น medium · เรียงรายการตามวันกำหนดส่ง (tech-lead เสนอ)
- F3: หมวดหมู่ — รายการหมวดแยก สร้าง / เปลี่ยนชื่อ / ลบได้, todo เลือกหมวดจากรายการ (0 หรือ 1 หมวด), ลบหมวดแล้ว todo ในหมวดนั้นกลายเป็น "ไม่มีหมวด" (ผู้ใช้)
- F4: กรองรายการ ตามสถานะ, หมวดหมู่, ลำดับความสำคัญ ใช้พร้อมกันได้ (ผู้ใช้ขอการกรอง · ตัวกรองที่ใช้ tech-lead เสนอ)
- F5: รันบน VPS ด้วย Docker — container เดียวให้บริการทั้ง API และหน้าเว็บ ข้อมูลอยู่ใน volume (ผู้ใช้เลือก VPS + Docker)

# Acceptance criteria
หมายเหตุ: ทุก endpoint อยู่ใต้ `/api` ส่วน `/` คือหน้าเว็บ ชื่อ field ละเอียดกำหนดใน architecture

- F1:
  - `POST /api/todos` body `{"title":"ซื้อนม"}` → 201 ได้ `id`, `title: "ซื้อนม"`, `done: false` และ `GET /api/todos` เห็นรายการนี้
  - `POST /api/todos` ที่ title ว่าง, มีแต่ช่องว่าง หรือยาวเกิน 200 ตัวอักษร → 422 และจำนวน todo ใน `GET /api/todos` ไม่เพิ่ม
  - `PATCH /api/todos/{id}` body `{"done":true}` → 200 `done: true` · body `{"done":false}` → `done: false` · body `{"title":"ซื้อนมจืด"}` → title เปลี่ยน
  - `DELETE /api/todos/{id}` → 204 แล้ว `GET /api/todos` ไม่มีรายการนี้ · `PATCH` / `DELETE` id ที่ไม่มี → 404
  - หน้าเว็บ `/`: พิมพ์ชื่อแล้วกดเพิ่ม → เห็นในรายการ · กดติ๊ก → แสดงว่าเสร็จ · แก้ชื่อได้ · กดลบ → หายไป · ทุกการกระทำยังคงอยู่หลัง reload หน้า
- F2:
  - `POST /api/todos` body `{"title":"a","due_date":"2026-12-31","priority":"high"}` → 201 ได้ค่าทั้งสองกลับมา · ถ้าไม่ส่ง → `due_date: null`, `priority: "medium"`
  - `due_date` ที่ไม่ใช่ YYYY-MM-DD หรือไม่มีจริง (`"31/12/2026"`, `"2026-02-30"`) → 422 · `priority: "urgent"` → 422
  - `PATCH /api/todos/{id}` แก้ `due_date`, `priority` ได้ · ส่ง `"due_date": null` → ลบวันกำหนดส่ง
  - `GET /api/todos` เรียงตาม `due_date` ใกล้สุดก่อน รายการที่ `due_date: null` อยู่ท้าย
  - หน้าเว็บ: เลือกวันกำหนดส่งและลำดับความสำคัญตอนเพิ่มและแก้ไขได้ และเห็นทั้งสองค่าบนแต่ละรายการ
- F3:
  - `POST /api/categories` body `{"name":"งาน"}` → 201 `{id, name}` · ชื่อซ้ำ → 409 · ชื่อว่าง / มีแต่ช่องว่าง / ยาวเกิน 50 → 422
  - `GET /api/categories` → 200 รายการหมวดทั้งหมด
  - `PATCH /api/categories/{id}` body `{"name":"งานด่วน"}` → 200 ชื่อใหม่ และ todo ในหมวดนั้นยังอยู่หมวดเดิม (`category_id` ไม่เปลี่ยน) · ชื่อซ้ำกับหมวดอื่น → 409 · ชื่อว่าง / มีแต่ช่องว่าง / ยาวเกิน 50 → 422 · id ที่ไม่มี → 404
  - `POST` / `PATCH /api/todos` ส่ง `category_id` ของหมวดที่มีอยู่ → บันทึกได้ · `category_id` ที่ไม่มี → 422 · ส่ง `null` → ไม่มีหมวด
  - `DELETE /api/categories/{id}` → 204, todo ที่เคยอยู่หมวดนี้ยังอยู่ครบและได้ `category_id: null` · id ที่ไม่มี → 404
  - หน้าเว็บ: สร้างหมวด, เปลี่ยนชื่อหมวด, ลบหมวด, เลือกหมวดตอนเพิ่ม / แก้ todo ได้ และเห็นชื่อหมวดบนแต่ละรายการ
- F4:
  - `GET /api/todos?status=active` ได้เฉพาะ `done: false` · `?status=done` ได้เฉพาะ `done: true` · ไม่ส่ง status → ทั้งหมด
  - `GET /api/todos?category_id=<id>` ได้เฉพาะหมวดนั้น · `?priority=high` ได้เฉพาะ high
  - ใช้หลายตัวกรองพร้อมกัน (เช่น `?status=active&priority=high&category_id=1`) → ได้รายการที่ตรงทุกเงื่อนไข
  - ค่าตัวกรองไม่ถูกต้อง (`?status=xxx`, `?priority=xxx`) → 422
  - หน้าเว็บ: เลือกตัวกรองแล้วรายการเปลี่ยนตามทันที และใช้หลายตัวกรองพร้อมกันได้
- F5:
  - `docker compose up -d --build` แล้ว `curl -i http://localhost:8000/` → 200 HTML ของหน้าเว็บ และ `curl http://localhost:8000/api/todos` → 200 JSON
  - เพิ่ม todo แล้ว `docker compose down && docker compose up -d` → todo ยังอยู่
  - มีคำอธิบายวิธีรันบน VPS ใน `README.md`

# นอกขอบเขต
- login / หลายผู้ใช้ / การกันการเข้าถึง (ผู้ใช้)
- ตั้ง domain, HTTPS, reverse proxy บน VPS — ผู้ใช้ทำเอง (tech-lead เสนอ)
- หลายหมวดต่อ todo, เวลาในวันกำหนดส่ง (tech-lead เสนอ)
- แจ้งเตือน, ค้นหาด้วยข้อความ, ลากเรียงลำดับ, backup อัตโนมัติ, rate limit (tech-lead เสนอ)

# ข้อจำกัด
- ใช้งานคนเดียว ไม่มี login (ผู้ใช้)
- ขึ้น server บน internet โดยไม่มีการกันการเข้าถึง ผู้ใช้ยอมรับว่าใครรู้ URL ก็อ่าน / แก้ / ลบได้ (ผู้ใช้)
- deploy บน VPS ของผู้ใช้ด้วย Docker (ผู้ใช้) · container เดียว (ผู้ใช้เลือกแนวทาง A)
- backend Python + FastAPI, frontend TypeScript + React, DB SQLite ไฟล์เดียวใน Docker volume (แนวทาง A)
- จำกัด input: ชื่อ todo 1–200 ตัวอักษร, ชื่อหมวด 1–50, วันที่ YYYY-MM-DD, priority low / medium / high (tech-lead เสนอ)
- หน้าเว็บภาษาไทย หน้าเดียว (tech-lead เสนอ)

# แนวทางที่พิจารณา
- A: container เดียว — Python + FastAPI + SQLite ให้บริการทั้ง API และไฟล์หน้าเว็บ (TypeScript + React build เป็น static) ข้อดี: deploy ตัวเดียว, origin เดียวไม่ต้องตั้ง CORS, FastAPI validate input ให้อัตโนมัติและมีหน้า API docs ในตัว ข้อเสีย: ใช้ 2 ภาษา (Python + TypeScript)
- B: container เดียว — TypeScript ทั้งหมด (Node + Fastify + SQLite และ React) ข้อดี: ภาษาเดียวทั้งระบบ ข้อเสีย: driver SQLite ของ Node เป็น native module build ใน Docker ยุ่งกว่าเล็กน้อย, ต้องเขียน schema validate เอง
- C: แยก 2 container — backend API + frontend (nginx) ต่อกันด้วย docker-compose ข้อดี: แยกอัปเดตแต่ละส่วนได้ ข้อเสีย: ต้องตั้ง CORS / proxy, config มากขึ้น เกินความจำเป็นสำหรับผู้ใช้คนเดียว
- เลือก: A เพราะ deploy ตัวเดียว, origin เดียว, FastAPI validate input ให้ ซึ่งสำคัญเมื่อเปิดสาธารณะ (ผู้ใช้เลือก)

# ข้อเสนอเพิ่มเติม (ยังไม่อยู่ใน spec)
